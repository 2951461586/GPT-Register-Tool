# Release notes

一个已发布的 tag 一份说明，文件名 `release-v<tag>.md`（如 `release-v2026.09.23.md`）。
它同时是 GitHub release 的**正文**来源 —— 用 `gh release create|edit --notes-file` 喂进去，
因此正文与文件必须**逐字节相同**。

## 格式（自 v2026.09.23 起）

只写两块：**新增功能**与**修复问题**。

```markdown
# v2026.09.23

<一到三行：本版范围 + 最值得注意的一两件事。>

## 新增功能

- **<功能名>** —— 用户能看到的行为变化；一句话说清「以前怎样 / 现在怎样」。
- **<功能名>** —— …

## 修复问题

- **<问题名>** —— 症状（含用户看到的具体错误码 / 文案）→ 根因 → 修法，一到两句。
- **<问题名>** —— …
```

### 规则

1. **只列新增功能与修复问题。** 不写验证过程、回滚路径、清理清单、实测对照表、代码片段、
   大段根因叙述。这些属于提交信息、`docs/audits/` 与工作区记忆，不属于发布说明。
2. **每条一个 bullet**，首句先给**用户可观察到的东西**（症状、错误码、新行为），再补根因
   与修法。读者是升级的人，不是改代码的人。
3. **覆盖范围 = 上一个发布 tag 到本 tag 的全部提交**，不是「今天干了什么」。
   漏掉的功能对升级者等于没做。核对命令：
   ```bash
   git log --oneline <上一个 release tag>..<本 tag>
   ```
4. **没有新增功能就删掉该标题**（不留空标题）；两节都空说明这个版本不该发。
5. **目标 ≤ 80 行。** 超出通常意味着你在写提交信息或审计报告。同一主题下多条相关改动
   合并成一个 bullet，不要一条提交一个 bullet。
6. **不回写历史**：本格式自 v2026.09.23 起适用，此前的说明保持原样。
7. **不要引用 gitignored 路径**（`runtime/`、`dist/` 等）。发布说明是公开文档，读者按
   这种路径跑不起来；要写「复现命令」就必须让脚本**已被跟踪**。

## 登记到索引

新发布的说明必须同时登记到 [`../README.md`](../README.md) 的 Release notes 段：
一行一条，摘要 ≤ 2 行。`scripts/docs_consistency_scan.py` 会钉住
「`README.md` / `README_EN.md` / `docs/README.md` 都指向最新一版说明」。

## 🔴 载荷一致性：改说明前必读

发布说明同时存在于**三处**，它们是三份独立副本：

| # | 位置 |
| --- | --- |
| 1 | GitHub release 正文 |
| 2 | 仓库里的本文件 |
| 3 | **安装包内副本** —— `docs/` 在打包载荷里，会随 zip 一起发出去 |

⇒ 改一行说明就要**重打资产**，否则第 3 份静默分叉（新旧 zip 可能只差几百字节，肉眼看不出）。
判据是把包内副本读出来与磁盘副本做内容比对，并抽查本次改动的具体字面量。

完整流程、判据与实测坑见技能 `release-notes-payload-consistency`。
